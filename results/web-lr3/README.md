# Web ЛР3. Вхід і доступ: докладно

Скорочений опис і таблиця пунктів - [README.md](../../README.md), розділ 6. Тут - механізм, повні результати дослідів і межі гарантій.

## Механізм

**Механізм: непрозорий токен у заголовку.** Вхід створює 32 випадкові байти (`secrets.token_urlsafe(32)`,
43 символи base64url) і рядок `session` із sha256 токена та `expires_at = now() + 8 год`; сам токен
повертається один раз і ніде не зберігається. Кожен запит шукає сесію за хешем у спільній базі, тому
вхід через app-a діє на app-b без спільної пам'яті процесів, а вихід видаляє рядок, і старий токен
одразу отримує 401 на обох екземплярах. JWT не обрано: вихід не знищив би токен до кінця строку
(розрив, який закриває лише Д3.1). Cookie не обрано: її браузер додає до запитів сам, тоді
знадобився б захист від CSRF. Пароль зберігається як argon2id (`argon2-cffi`, типові параметри:
64 МіБ, 3 проходи); невідомий логін перевіряється з фіктивним хешем тих самих параметрів, тож відповідь
однакова й за тілом, і за часом. Перевірка хеша виконується в потоці поза циклом подій, не більше
`LOGIN_CONCURRENCY` = 4 одночасно на процес, щоб сплеск входів не вичерпав пам'ять.

**Де клієнт зберігає токен.** У пам'яті модуля `api.ts` і в `sessionStorage` вкладки: токен переживає
перезавантаження сторінки, але не потрапляє в інші вкладки й зникає з закриттям вкладки. Будь-який
скрипт цього походження може його прочитати (XSS), тому клієнт не завантажує сторонніх скриптів, а
сервер обмежує строк сесії 8 годинами. Відповідь 401 на запит із токеном стирає сесію в клієнті й
повертає на сторінку входу.

**Власник у SQL і 404 замість 403.** Перевірка власника - частина самого запиту: `GET`, `PATCH` і
`cancel` мають `WHERE id = %s AND user_id = %s`, а список - `WHERE user_id = %s`; окремого кроку
«прочитати, потім перевірити», який можна забути в іншому маршруті, немає. Чуже бронювання й
неіснуюче дають той самий 404 `booking-not-found` з тим самим текстом: 403 підтвердив би, що такий id
існує в когось іншого. Ключ ідемпотентності належить користувачу сесії (`(user_id, operation, key)`):
той самий ключ від іншого користувача створює окреме бронювання й не повертає чужої відповіді
(`test_lr3.py::test_8`).

**Функція персоналу.** `POST /v1/levels/{id}/close` (`x-course: staff-action`) перевіряє роль до
будь-якої дії: користувач отримує 403 навіть для неіснуючого рівня, тож відповідь не розкриває
каталог рівнів. Повтор - 200 з тим самим станом. Закриття забороняє лише нові бронювання (409
`level-closed`, рівень читається в транзакції бронювання), підтверджені лишаються чинними (рішення B8).
`POST /v1/levels/{id}/open` - зворотна дія для демонстрації. Каталог (`GET /v1/garages`,
`GET /v1/levels/{id}/hours`) відкритий без входу (M10).

**CORS і CSRF.** Сервер дозволяє рівно `CLIENT_ORIGIN` (`http://localhost:5173`), без `*` і без
віддзеркалення `Origin`; методи GET, POST, PATCH, OPTIONS; заголовки `Authorization`, `Content-Type`,
`Idempotency-Key`, `If-Match`, `X-Request-ID`; відкриті клієнту `Location`, `ETag`, `Retry-After`,
`X-Request-ID`, `Idempotent-Replayed`, `X-Instance`; `allow-credentials` не вмикається, бо cookie немає.
CORS не є захистом від CSRF: він лише вирішує, чи дасть браузер сторінці іншого сайту **прочитати**
відповідь, а простий запит (форма, GET) до сервера все одно доходить і виконується. Від CSRF захищає
сам механізм входу: токен лежить у `sessionStorage` походження клієнта, сторінка іншого сайту не може
його прочитати, а браузер ніколи не додає заголовок `Authorization` сам. Тому будь-який запит, який
може надіслати сторонній сайт, приходить без особи користувача й отримує 401 до дії; перевірка
`Sec-Fetch-Site` чи `Origin`, потрібна для cookie, тут нічого не додала б. Сторінка
`web/tools/evil-origin/` показує три спроби: POST із JSON (браузер не надсилає його після відмови
preflight), простий GET каталогу (сервер відповів 200, але браузер не дав сторінці прочитати відповідь)
і HTML-форму (надіслана, сервер відповів 401).

```bash
python -m http.server 8082 --bind 127.0.0.1 --directory web/tools/evil-origin
```

Тести: `test_lr3.py` - 13 тестів (усього 41 з `test_lr1.py`, `test_lr2.py`, `test_rules.py`); стенд
`docker compose up -d nginx publisher`, команда та сама, що в ЛР1.

## Межі гарантій

Керованих відмов ЛР3 не додає. Що підтверджено й що ні:

- Вихід знищує сесію на сервері, але токен, перехоплений до виходу, діє до виходу або до кінця 8 годин;
  іншого відкликання (наприклад, «вийти на всіх пристроях») немає.
- Час відповіді на неправильний пароль і невідомий логін вирівняно однією перевіркою argon2id; виміряно
  медіану 15 спроб на одному екземплярі без навантаження, а не статистичну нерозрізненність.
- Кількість спроб входу не обмежена (Д3.3 не виконувався): перебір паролів сповільнює лише вартість argon2.
  `LOGIN_CONCURRENCY` = 4 обмежує одночасні перевірки на процес, решта чекає в черзі без тайм-ауту.
- Токен у `sessionStorage` доступний будь-якому скрипту походження клієнта; захист від XSS - відсутність
  сторонніх скриптів і екранування React, окремої політики CSP немає.
- Прострочені сесії відхиляються одразу (`expires_at > now()` у запиті), а `publisher` лише прибирає їх
  порціями раз на хвилину; якщо `publisher` зупинено, таблиця росте, але доступ не змінюється.
- CORS перевірено для одного дозволеного походження і одного стороннього; nginx пропускає `OPTIONS` до
  app-a/app-b, preflight обробляє `CORSMiddleware` (відповідь 200, не 204).
- Сторінки DPC («Barrier», «Compute») мають власний токен DPC (`VITE_DPC_TOKEN`) і від входу Web не залежать.
